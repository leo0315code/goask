# GoAsk 架构设计文档

> 版本：v1.0（2026-10-24）
> 技术栈：Go + MySQL + Gin + GORM + JWT

## 1. 背景与目标

GoAsk 是一个类 Stack Overflow 的问答社区后端系统，提供用户注册登录、提问、回答、评论、投票、采纳答案、标签、中文全文检索等能力。

**设计目标：**

- 可直接上线：具备健康检查、优雅停机、限流、统一错误码、结构化日志等生产要素；
- 水平可扩展：服务无状态（JWT），数据库单点起步，预留读写分离与缓存接入点；
- 可维护：清晰的分层与依赖方向，业务逻辑可脱离数据库单元测试；
- 可部署：一条 `docker compose up` 即可拉起完整服务，或用二进制 + 外部 MySQL 部署。

**v1 非目标（Roadmap 见第 9 节）：** 私信、通知推送、富文本编辑器、管理后台 UI、分布式检索（ES）、对象存储。

## 2. 功能范围（v1）

| 模块 | 能力 |
| --- | --- |
| 用户 | 注册、登录（JWT）、获取/修改个人资料、封禁状态校验 |
| 问题 | 发布、编辑（仅作者）、删除（作者/管理员）、列表（最新/热门/未回答/按标签）、详情（浏览计数）、关闭 |
| 回答 | 发布、编辑（仅作者）、删除（作者/管理员）、按问题列出 |
| 采纳 | 提问者采纳一个回答（唯一），可更换 |
| 投票 | 对问题/回答 +1 / -1，可切换、可撤销，计数与声望同步更新 |
| 评论 | 对问题/回答发表评论、列出评论 |
| 标签 | 打标签（自动创建）、标签列表（按问题数排序）、按标签检索问题 |
| 检索 | 标题 + 正文中文全文检索（MySQL ngram 全文索引） |

## 3. 总体架构

```
                    ┌────────────────────────────────────────────┐
   Client (Web/App) │                 GoAsk 服务                  │
        ───────────►│  ┌──────────────────────────────────────┐  │
        HTTP/JSON   │  │  Router (gin.New)                    │  │
                    │  │  ├── Recovery / RequestLogger (slog) │  │
                    │  │  ├── CORS                            │  │
                    │  │  ├── RateLimit (per-IP 令牌桶)        │  │
                    │  │  └── Auth (JWT, required/optional)   │  │
                    │  └───────────────┬──────────────────────┘  │
                    │                  ▼                          │
                    │  ┌──────────────────────────────────────┐  │
                    │  │  Handler 层：参数绑定/校验、响应封装   │  │
                    │  └───────────────┬──────────────────────┘  │
                    │                  ▼                          │
                    │  ┌──────────────────────────────────────┐  │
                    │  │  Service 层：业务规则、权限、编排       │  │
                    │  └───────────────┬──────────────────────┘  │
                    │                  ▼                          │
                    │  ┌──────────────────────────────────────┐  │
                    │  │  Repository 层：GORM 数据访问          │  │
                    │  │  （跨表一致性操作在单事务内完成）        │  │
                    │  └───────────────┬──────────────────────┘  │
                    └──────────────────┼──────────────────────────┘
                                       ▼
                              MySQL 8 (utf8mb4)
                              启动时自动执行迁移
```

**依赖方向**：`handler → service → repository → model`，公共能力（错误、JWT、密码、响应、分页）沉到 `internal/pkg`，不允许反向依赖。service 依赖 repository 的**接口**而非具体实现，便于单元测试时用内存假实现替换。

## 4. 技术选型

| 选择 | 理由 |
| --- | --- |
| Gin | 生态最成熟、性能足够；`gin.New()` 挂自定义中间件，日志接入 slog |
| GORM | 开发效率高，模型即文档；事务/钩子能力满足计数器一致性需求 |
| MySQL 8 + ngram 全文索引 | 单存储组件即可支撑中文检索，运维成本最低；数据量到千万级再引入 ES |
| JWT (HS256) | 无状态认证，横向扩展不需要 session 共享；短期令牌（默认 72h，可配） |
| bcrypt | 密码哈希标准做法，自带盐，抗 GPU 暴破 |
| slog（标准库） | 结构化 JSON 日志，零第三方依赖，可对接任意采集器 |
| golang.org/x/time/rate | 轻量令牌桶，按 IP 维度做全局限流 + 认证接口严限流 |
| 内嵌 SQL 迁移器 | 启动时按序执行 `migrations/*.sql`，`schema_migrations` 表记录版本，无需额外 CLI |

## 5. 分层职责

- **cmd/server**：组装依赖（config → DB → 迁移 → store/repos → services → router → http.Server），持有优雅停机逻辑。
- **handler**：只做协议层工作——绑定/校验请求、调用 service、用统一响应结构返回；不出现 SQL 与业务规则。
- **service**：业务规则（谁能编辑/删除、参数合法性、目标是否存在、采纳归属校验等），编排 repo 调用。
- **repository**：数据访问；**所有跨行/跨表的一致性变更（投票、回答、采纳、删除）在单个数据库事务内完成**。
- **middleware**：认证（required/optional 两种）、CORS、限流、请求日志、panic 恢复。
- **internal/pkg**：`apperr`（业务错误码）、`httpx`（统一响应/分页解析）、`jwtx`、`passwordx`。

## 6. 关键设计决策

### 6.1 认证与权限
- 登录成功签发 `HS256` JWT，claims：`sub`（用户 ID）、`iat`、`exp`、`iss=goask`。
- 密码策略：8–72 位；bcrypt cost 12（可配）。
- 权限模型两级：`user` / `admin`。作者可编辑/删除自己的内容；`admin` 可删除任何内容、封禁用户入口预留。
- 封禁用户（`status=banned`）登录时直接拒绝，存量 token 通过每次请求校验状态兜底（详情/写操作路径会加载用户）。

### 6.2 投票的一致性
投票涉及三处数据：`votes` 行、目标表计数器、作者声望。采用**单事务 + upsert 语义**：

- 无投票 → 插入（value=±1），计数 +1，声望调整；
- 与已投方向相同 → 删除该票（撤销），计数 -1，声望回退；
- 与已投方向相反 → 更新方向，两个计数器一增一减，声望按全量差值调整。

计数器冗余在 `questions`/`answers` 表上（`upvote_count`/`downvote_count`），列表页零 JOIN 取数；事务保证与 `votes` 表不漂移。声望规则：回答被赞 +10、问题被赞 +5、被踩 -2、被采纳 +15，撤销全部对称回退。

### 6.3 热度排序
简单可解释的 Reddit 式衰减公式，纯 SQL 计算无需额外组件：

```
score = (upvote_count - downvote_count + answer_count) / POWER(天数 + 2, 1.5)
```

### 6.4 中文全文检索
`questions(title, content)` 建立 `FULLTEXT ... WITH PARSER ngram`（ngram_token_size 默认 2），检索用 `MATCH ... AGAINST(? IN NATURAL LANGUAGE MODE)`。缺点是最小分词为 2 字、无拼音纠错，数据量大后 Roadmap 中换 ES。

### 6.5 限流
两级令牌桶，按客户端 IP（信任 `X-Forwarded-For` 首跳，需部署在可信反代后）：
- 全局：默认 120 req/min/IP；
- 认证接口（注册/登录）：默认 10 req/min/IP，防撞库与暴力注册。

超限返回 HTTP 429 + 错误码 `42900`。桶使用 `sync.Map` + 定期清理，避免内存泄漏。

### 6.5a 防恶意注册与灌水
- **图形验证码**：注册必须先 `GET /auth/captcha` 领取一次性算术题（内置 SVG 渲染 + 干扰线，5 分钟有效、用后即焚），无外部服务依赖；
- **注册开关与邀请码**：`REGISTER_ENABLED` 一键关闭开放注册；`REGISTER_INVITE_CODE` 开启邀请制；
- **同 IP 注册限额**：默认 3 个/日/IP（内存滑动窗口）；
- **发布频次**：问题 60s 间隔 / 20 条每 24h，回答 30s / 50，评论 10s / 200——由 `SpamGuard` 在 service 层统一检查，数据来自数据库（多实例部署同样生效）；
- **重复内容拦截**：同一用户 24h 内发布完全相同的标题/正文直接拒绝；
- 所有阈值集中在 `internal/service/antispam.go` 的 `spamRules`，可按站点情况调整。

### 6.6 统一响应与错误码

```json
// 成功
{"code": 0, "message": "ok", "data": { ... }}
// 失败
{"code": 40900, "message": "用户名或邮箱已被注册", "data": null}
```

| code | HTTP | 含义 |
| --- | --- | --- |
| 0 | 200 | 成功 |
| 40000 | 400 | 参数错误 |
| 40100 | 401 | 未登录 / token 无效或过期 |
| 40300 | 403 | 无权限 |
| 40400 | 404 | 资源不存在 |
| 40900 | 409 | 状态冲突（重复注册、重复采纳等） |
| 42200 | 422 | 业务校验失败 |
| 42900 | 429 | 请求过于频繁 |
| 50000 | 500 | 服务器内部错误 |

### 6.7 优雅停机与健康检查
- `SIGTERM/SIGINT` → `http.Server.Shutdown(ctx, 10s)` 排空在途请求 → 关闭 DB 连接；
- `GET /healthz` 存活探针（不查库）；`GET /readyz` 就绪探针（`SELECT 1`），供 LB/K8s 摘流量。

### 6.8 配置
全部通过环境变量注入（12-Factor），支持 `.env`（本地开发）；`JWT_SECRET` 未设置时启动即失败，杜绝弱密钥上线。完整清单见 README「配置项」。

## 7. 安全设计

- **SQL 注入**：全量 GORM 参数化，无字符串拼接用户输入；
- **密码**：bcrypt 哈希存储，任何接口不回传 `password_hash`；
- **JWT**：密钥仅服务端持有；token 过期/篡改统一 401；
- **越权**：编辑/删除/采纳均在 service 层做所有权校验，返回 404/403 而非泄露他人内容；
- **滥用防护**：认证接口按 IP 严限流；注册字段长度/格式服务端强校验；
- **CORS**：白名单可配，生产必须收敛到具体域名；
- **内容**：正文按纯文本/Markdown 存储，XSS 防护由前端渲染层负责（转义或安全渲染器），接口层对长度做限制。

## 8. 部署与运维

- **Docker**：多阶段构建，静态编译（CGO_ENABLED=0），运行镜像 alpine + 非 root 用户 + HEALTHCHECK；
- **docker compose**：`mysql:8.0`（utf8mb4、数据卷、健康检查）+ 应用容器，应用启动时自动迁移；
- **日志**：JSON 到 stdout，交由采集器（loki/filebeat 等）处理；
- **水平扩展**：服务无状态，直接多副本 + LB；数据库先垂直扩，读多写少场景可加只读副本（repo 层已隔离查询入口）；
- **备份**：MySQL 定期 `mysqldump`/快照，`schema_migrations` 保证迁移幂等可重放。

## 9. Roadmap（v1 之后）

1. 站内通知（被回答/被采纳/被评论），表已预留扩展位；
2. 管理后台（用户封禁、内容下架、数据看板）；
3. 缓存层（Redis：热点问题列表、计数器缓冲、限流上移）；
4. ES/Meilisearch 检索 + 同义词、拼音；
5. Markdown 渲染与图片上传（对接对象存储）；
6. OpenAPI 规范文件与前端 SDK 自动生成。
